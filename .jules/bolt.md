## 2024-07-23 - Avoid Chained Array Iteration on Large Collections
**Learning:** In frontend functions operating on state collections (like calculating aggregate values over `s.ledger` or `s.hist`), chaining `Array.prototype.filter().reduce()` allocates intermediate filtered arrays and iterates the collection multiple times. In a framework-less vanilla DOM architecture like this one where rendering cycles might be triggered often, this creates unnecessary overhead and GC pressure.
**Action:** Collapse these into single imperative `for...of` passes, maintaining accumulator variables, to iterate only once and avoid array allocations.

## 2025-02-12 - Date String Sorting Optimization
**Learning:** `String.prototype.localeCompare()` is significantly slower than standard string comparison operators (`<`, `>`). Since the application stores dates as ISO-like 'YYYY-MM-DD' strings, we can safely replace `localeCompare()` with `<` and `>` when sorting arrays by date. This avoids locale-aware comparison overhead while maintaining correct chronological ordering.
**Action:** Always prefer standard string inequality operators (`<`, `>`) when sorting standard ISO-like date strings. Reserve `localeCompare()` for sorting names or other strings where locale-specific sorting rules (like accents or capitalization) are actually required.

## 2025-02-23 - Replace reduce with for loops
**Learning:** In hot loops, replacing array methods like reduce with imperative for loops avoids intermediate allocations and reduces Garbage Collection (GC) overhead.
**Action:** Use direct imperative iteration for scalar accumulation in frequently updated computations to improve speed.

## 2025-02-24 - Function Re-allocation in Sort Callbacks
**Learning:** Defining helper arrow functions directly inside loop callbacks like `Array.prototype.sort()` causes the function to be needlessly re-created in memory on every comparison ($O(N \log N)$ times). While modern JS engines try to optimize this, it's safer and structurally cleaner to declare loop-invariant closures outside the hot loop.
**Action:** Always hoist helper function definitions out of high-frequency loop or sorting callbacks to prevent unnecessary memory reallocation and overhead.

## 2025-02-24 - Replace chained array combinations in rendering filters
**Learning:** In functions that filter collections on UI state changes (like `_tcApplyLedgerFilter`), chained methods like `.filter().some()` create multiple intermediate arrays and add significant GC overhead (O(N) allocations) on every re-render.
**Action:** Collapse complex chained filtering logic into a single imperative loop using early `continue` statements to prevent intermediate array allocations and improve UI responsiveness.
## 2025-02-28 - Loop Fusion in POS Cart Evaluation
**Learning:** In the POS cart evaluation (`posGenerateSaleQR` and `posCheckout`), chaining `.some()` to check for missing FX rates and `.reduce()` to calculate the total sum creates multiple O(N) array traversals. Fusing these checks into a single imperative loop eliminates redundant iterations and improves performance for larger cart sizes.
**Action:** When evaluating an array for a condition and simultaneously accumulating a sum, combine them into a single imperative loop instead of chaining array methods.
## 2025-03-01 - Avoid nested O(N*M) lookups in template generation
**Learning:** Generating dropdown options using `.filter(order => !matches.some(m => m.orderNumber === normalizeShippingOrderNumber(order.num)))` creates an O(N*M) bottleneck, where M is the small set of matches but `normalizeShippingOrderNumber` is unnecessarily called N*M times.
**Action:** Replace nested array lookups involving expensive normalization calls with O(1) Set lookups initialized beforehand, and use a single imperative loop to build output strings.
## 2025-03-02 - O(N) max finding instead of O(N log N) sorting
**Learning:** Using chained array methods like \`slice().sort((a,b) => ...)[0]\` to find a minimum or maximum element introduces an unnecessary $O(N \log N)$ time complexity and an extra array allocation.
**Action:** Replace these operations with a single imperative $O(N)$ loop to find the minimum or maximum element. It avoids allocations and is substantially faster.

## 2026-09-05 - Per-expense recompute of per-file data in receipt matching
**Learning:** `receipt-match.js`'s `bestMatch()` maps every expense through `scoreMatch(fileInfo, exp)`, but `scoreMatch` derived `fileDate`/`money` from `fileInfo.name` fresh on every call — work that only depends on the file, not the expense being scored. `amountFromName` also compiles a new `RegExp` per call, so this was recompiling the same regex against the same filename once per expense (O(files × expenses) regex compiles instead of O(files)). A synthetic benchmark (80 files × 400 expenses) went from ~168ms/run to ~120ms/run (~29% faster) after hoisting.
**Action:** When a batch scoring/matching function loops a per-item scorer over a candidate list, check whether the scorer recomputes anything derived only from the fixed item (not the candidate) — hoist that into the caller and pass it in, rather than letting it get recomputed once per candidate.

## 2026-09-06 - O(N*M) full-history rescan in dedup, called on every ledger edit
**Learning:** `inventory.js`'s `deduplicateDirectConsignmentSales()` calls `s.hist.findIndex(...)` once per consignment sale (twice, across its two match passes) to find a duplicate Direct-sale mirror — an O(hist × consignmentSales) walk. This function runs inside `recomputeAfters()`, which fires after essentially every ledger/history mutation (recordOrder, void, edit, sync merge — 18 call sites in main.js), so it's not a cold path: it's on the critical path of every single order action, and it gets slower every year a book stays active and its history grows. A synthetic benchmark (~5,300 history rows, realistic qty/date spread) went from ~76ms to ~3ms (~23x) after indexing.
**Action:** Since every match requires exact `qty` equality (and pass 1 also requires exact `date` equality) before the price epsilon check ever runs, bucket eligible candidates into a `Map` keyed by `qty` (and `qty`→`date`) up front, built by one pass over history, then have each lookup scan only its bucket. Preserves "first match in original array order" exactly since buckets are filled in original iteration order. When a hot function is called from many mutation call sites rather than one obvious place, greping call counts across the codebase before assuming it's cold is worth the extra minute.

## 2026-09-08 - Raw `oninput` handlers wired straight to full-rebuild renders
**Learning:** `filterCustomers()` (bound via `oninput="filterCustomers(this.value)"` on `#cust-search`) called `renderCustomers()` synchronously on every keystroke, which calls `buildCustomerList()` — a full scan of every book's `hist`, the unapplied `orders` array, and the Stripe pull cache — then rebuilds the whole buyer table's `innerHTML`. None of the other `oninput`-wired handlers in `main.js` are debounced either, so any search/filter box driving an aggregation over the full order history (not just a plain array filter) pays that cost per character typed, not per search. Memoizing `buildCustomerList()` itself was rejected as too risky here: its inputs (`states[*].hist`, `orders`, the Stripe cache) are touched by ~18+ mutation call sites with no existing dirty-flag/version counter, so a length-based or similar cache signature could easily miss an in-place mutation (e.g. voiding a history row flips `.voided` without changing `hist.length`) and show stale buyer data in a financial app.
**Action:** When a search/filter input's handler re-derives an expensive aggregate (not just re-filtering an already-built array), debounce the render call itself (~150-200ms via a module-level `setTimeout`/`clearTimeout` pair) rather than trying to cache the aggregate — it's far lower-risk than threading cache invalidation through every mutation site, and it's safe as long as the input element isn't inside the DOM subtree that gets replaced by the render (check that before assuming no focus-loss risk).

## 2026-09-10 - `reconcileShippingExpense()` re-normalized every order, once per expense, per sweep
**Learning:** `reconcileShippingExpense()` (`shipping-reconciliation.js`) is a per-expense pure function, but its three callers in `features/shipping.js` (the Shippo bulk import, the Canada Post sweep, the shipping-email sweep) all loop it over many expenses/transactions against the *same* `orders` array reference for the whole sweep. Every call re-ran `normalizeShippingOrderNumber`/`normalizeTrackingNumber`/`normalizeText`/`normalizePostal` on every order from scratch — none of which depend on the expense being scored, only on the order — so a sweep cost O(orders × expenses) regex/string work. A synthetic benchmark (500 orders × 300 expenses, matching on the tracking-number tier — the common case for a real label) went from ~70ms to ~3.6ms (~19x) after caching a normalized index per `orders` array reference in a `WeakMap` (a fresh order list — e.g. a later sweep's rebuilt list — naturally misses and recomputes, so nothing needs manual invalidation). Note: a synthetic mix that instead forces most expenses down to the fuzzy-name fallback barely benefits, since Levenshtein distance is inherently O(candidates) and depends on both expense and order name — the caching only removes the *normalization* cost, not the fuzzy comparison itself.
**Action:** When a pure single-item "score/match against a candidate list" function is called in a loop with the *same* candidate list across iterations (check callers, not just the function itself), and only the item side actually varies, cache a precomputed index of the candidate list keyed by the list's object reference (`WeakMap`) rather than threading a cache-invalidation signal through every mutation site — the reference itself is the signal, since a genuinely changed list is, in this codebase's pattern, always rebuilt as a new array rather than mutated in place. Verify that assumption for the specific caller before relying on it.

## 2026-09-11 - Sibling render functions in shipping.js can carry the identical N*M bug independently
**Learning:** `buildShippingWeightBandHtml()` (`features/shipping.js`) called `BOOK_LIST.find()` and `shippoExpenses.filter(... normalizeShippingOrderNumber(e.shippingOrderNumber) ...)` once per order — O(orders × books + orders × expenses) — despite its neighbor `buildShippingPnLHtml()`, defined ~500 lines above it in the same file, already carrying a "⚡ Bolt Optimization" comment for the exact same fix (a `shippoExpensesByOrder` Map). Both functions are called back-to-back from the same `allOrders`/`shippoExpenses` in the shipping-analysis hub render, so the earlier fix did not propagate even though the pattern and the fix are identical. A synthetic benchmark (6,000 orders × 3,000 expenses, 40 books) went from ~2115ms to ~2.6ms (~827x) after adding a `bookById` Map and a `matchedExpensesByOrderNumber` Map, built once before the order loop instead of re-filtering per order.
**Action:** When one function in a file already has a "⚡ Bolt Optimization" Map-based fix for an O(N×M) lookup, grep sibling functions in the *same file* for the same raw pattern (`.find(`/`.filter(` on the same two collection names) before assuming the category is covered — a prior fix to one function is not evidence its neighbors were checked.
